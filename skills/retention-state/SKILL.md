# Retention State

Design retention through accumulated value: reputation, audience, data, relationships, progress, or workflows that make future use more useful.
Habit is repeated behavior; state is value retained from prior use. A streak can record meaningful progress but cannot repair a weak core product.

Do NOT use for cancellation flows, save offers, dunning or win-back campaigns. Route first-value and activation problems to `onboarding-activation`, engagement measurement to `power-user-curve`, and retention economics to `saas-unit-economics-audit`.

## Inputs and evidence

| Input | Needed detail | If missing |
|---|---|---|
| Product | Recurring job, user, payer, natural usage cadence | Use supplied materials; label inferred facts [Assumption] and unknowns [Unknown] |
| Retention | Cohort curve, core action, activation event | Continue qualitatively with [No cohort data]; do not invent rates or lift |
| State | What users accumulate, and how it improves future value | Use documented behavior; mark unverified accrual [Unknown] |
| Portability | What can be exported, transferred or recreated | Read available documentation; otherwise mark [Unknown] |
| Constraints | Privacy, consent, trust, sensitive records | State unresolved constraints before proposing shared state |

Proceed with useful draft work from the supplied inputs. Separate observed facts, assumptions, hypotheses and unknowns. Ask only when missing information changes permission, scope or material risk.
Treat examples as illustrations rather than benchmarks. Never claim to have inspected a product or executed a sibling skill without evidence.

## Mode and layer routing

- **Diagnostic** (default): choose the best state type.
- **State audit**: inspect existing deposits and portability; identify missing compounding value.
- **Investor lens**: distinguish evidenced switching costs from speculative defensibility.
- **Streak design**: apply the core-loop check and streak specification below.
- **Unclear retention problem**: determine the failing layer first. First value goes to `onboarding-activation`; product-fit doubts go to `customer-research` and `growth-strategist`; acquisition mismatch goes to `channel-fit-diagnostic`. Cancellation interventions need a separate workflow.

When routing out, give the destination, reason, supplied evidence, missing evidence and next deliverable, then stop the unrelated design work. A handoff is a draft, never a claim that the destination ran.
If the architecture check fails, continue to choose valuable state; do not lead with cancellation tricks or reminders.

## Procedure

1. **Check the architecture.** Answer two questions with evidence or an explicit unknown: does the product get better with use, and does the user build valuable state they would lose by leaving? If both are no, diagnose an architecture gap. If one is no, name the missing half. A persistent pseudonymous identity can accumulate state; pure anonymity generally cannot.
2. **Map all eight state types.** Score fit, current accrual, compounding potential, portability and risk. Keep each row concise.
3. **Choose one primary state.** Pick the strongest natural fit and propose three to five feature-level changes. Avoid a collection of shallow mechanics.
4. **Design compounding.** Show deposit → better future value → next deposit. Where appropriate, use a shared data asset, permissioned sharing with a non-customer, or reusable public templates. Do not force sharing of private records.
5. **Accelerate the first deposit.** Identify the first useful saved item, relationship, review, integration or derived insight. Send activation changes to `onboarding-activation` with a draft brief.
6. **Run the ethics and portability checks.** State what users can take with them and what value remains. Preserve usable export. Replace coercive friction with derived utility, trust or collaboration.
7. **Define measurement.** Select a state-accrual metric, the cohort retention curve it should affect, and a testable hypothesis. Use `power-user-curve` for engagement depth and `experiment-design` for causal testing; use `saas-unit-economics-audit` for economics.

## State scorecard: eight types

| Type | Value that accrues | Portability and design question |
|---|---|---|
| Reputation | Reviews, verified history, trust or credentials | Can earned trust improve discovery while ratings remain honest and contestable? |
| Audience | Followers, subscribers or reachable demand | What value remains when users export their audience? Preserve usable export. |
| Data | History, preferences, derived analytics or learned context | Does usage improve decisions or output beyond merely storing records? |
| Social graph | Relationships and useful interaction density | Does collaboration become more useful as relevant connections grow? |
| Progress and streaks | Learning, achievements and a visible record of investment | Is the underlying action valuable at its natural cadence? |
| Embedded workflows | Configurations, integrations, automations and routines | Is the integration useful rather than artificially difficult to replace? |
| Marketplace access | Relevant supply, demand or verified participation | Is any exclusivity legitimate, and does access deliver ongoing utility? |
| Trust-sensitive continuity | Reliable handling of important records or processes | Can continuity improve without exploiting fear or withholding records? |

For data state, distinguish stored history from derived value. In an assistant, memory reused and useful connectors may improve results. Provide consent, inspection, correction and deletion controls; do not share sensitive context by default.
Per-user or per-team learning is a switching cost, not automatically a network effect. Only claim a network effect when one user's participation demonstrably improves value for others; route its design to `product-led-acquisition`.

## Streak design

Use this section whenever the request mentions streaks, habits or gamification, or progress is the primary state.

**Core-loop check:** require evidence that users already value the recurring action and that the cadence fits the job. If evidence is missing, mark the design provisional and propose a test. If the loop is weak, stop streak design and route core-value research to `customer-research` or first-value work to `onboarding-activation`.

- Count the smallest meaningful unit of real use, not the easiest click.
- A skip, pause or snooze never extends a streak. Planned breaks belong in a flexibility schedule: distinguish preserving an existing streak from earning a new period.
- Match cadence to natural use; do not prescribe daily activity for a naturally weekly or infrequent job.
- Consider more flexibility early and less added flexibility later; treat the schedule as a hypothesis to test rather than a universal threshold.
- Pair leniency with a meaningful counterweight, such as a no-freeze marker, and name the person responsible for preserving the mechanic's meaning.
- Design the core loop, longer-term goals and profile record together. Keep prominence proportional to useful progress.
- Propose consent-based reminder timing tests. Respect time zones, preferences and opt-outs. Drafting a reminder does not authorize sending it.
- Measure later retention as well as immediate activity. Stop neutral experiments that add needless interface complexity.

Include this specification:

| Field | Required decision |
|---|---|
| Core-loop check | Pass, fail or unknown, with evidence |
| Unit of use | Meaningful action that extends the streak |
| Cadence | Period and reason |
| Flexibility schedule | Initial allowance, cap, taper and treatment of breaks |
| Perfection marker | Signal for periods completed without a freeze |
| Keeper | Role responsible for the mechanic's meaning |
| Prominence | Where the streak appears and how often |
| Reminder rule | Proposed timing, consent and opt-out behavior |
| Guardrail metrics | Current-user retention, weekly return, meaningful task completion and reminder opt-outs |
| First three experiments | Hypothesis, comparison, metric and read date, including a later retention read |

## Output contract

1. **Pre-check and state scorecard:** two architecture answers above one compact eight-row table with fit (strong/weak/none/unknown), current deposit, compounding potential, portability and risk.
2. **Primary state and product changes:** one state to build first, why it fits, and three to five concrete changes.
3. **Compounding loop:** deposit → improved future value → next deposit; explain any shared artifact and its access controls.
4. **First-deposit plan:** activation change, metric and any draft handoff.
5. **Retention measurement:** state-accrual metric, cohort definition, observation period and decision rule. Without cohort data, label impact unknown and specify what data to collect.
6. **Ethics check:** value creation versus coercive lock-in, export usability, privacy and regret risks.
7. **Streak specification:** include the complete table only when progress is primary or the request explicitly asks for streak design; record a failed core-loop check instead of forcing a spec.
8. **Investor verdict, when requested:** say what evidence supports stickiness, what remains unproven and whether learning benefits one user/team or others. Do not declare an unbreakable moat from memory alone.

## Guardrails

- All outputs, including routed handoffs, are drafts. Explicitly require user approval before any live product edit, rollout, migration, reminder send or irreversible action. Never claim execution without evidence.
- Preserve usable export; approval does not justify hostage mechanics or degraded portability.
- Do not retain sensitive data without a valid user need and clear controls.
- Do not infer causality from retained-user correlation. Compare matched cohorts cautiously and test the proposed change before scaling it.
- State cannot excuse a broken core job. Build useful value rather than artificial switching friction.
